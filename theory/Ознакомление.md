# Kotlin: типы, null safety и функции

## Введение

Kotlin — статически типизированный язык, который сегодня является основным для разработки Android-приложений. В отличие от Java, он переносит контроль над `null` из плоскости «соглашений и аннотаций» в систему типов: компилятор заранее знает, может ли переменная быть `null`, и не даёт выполнить потенциально опасную операцию без явного подтверждения. Ниже последовательно разобраны все пункты плана, а в практической части небольшая модель товара переносится с «небезопасного» стиля на идиоматичный Kotlin.

---

## 1. `val` и `var`

В Kotlin объявление переменной начинается с ключевого слова, а не с типа:

```kotlin
val appName = "Shop"     // неизменяемая ссылка (аналог final в Java)
var counter = 0          // изменяемая ссылка
counter++                // допустимо
// appName = "Other"     // ошибка компиляции
```

* `val` — ссылка присваивается один раз. Это значение по умолчанию для локальных переменных, параметров и свойств.
* `var` — используется только там, где значение действительно меняется (счётчик, состояние UI, накопитель в цикле).

Важно: `val` гарантирует неизменяемость *ссылки*, а не объекта. `val list = mutableListOf(1)` запрещает переприсвоить `list`, но не запрещает `list.add(2)`. Для настоящей неизменяемости применяют `List`, `data class` с `val`-свойствами и т. п.

---

## 2. Вывод типов (type inference)

Тип можно не указывать, если компилятор выводит его из инициализатора:

```kotlin
val count = 42                 // Int
val ratio = 0.5                // Double
val title = "Кофе"             // String
val items = listOf("a", "b")   // List<String>
val pair = 1 to "one"          // Pair<Int, String>
```

Вывод работает и для функций с телом-выражением (см. п. 7). Правило хорошего тона: тип можно опускать в локальных переменных и приватных функциях, но для публичного API (public-функции, свойства класса, возвращаемые типы) его лучше указывать явно — это фиксирует контракт и защищает от случайного изменения сигнатуры при рефакторинге.

---

## 3. Nullable-типы

Главное отличие от Java: `String` и `String?` — **разные типы**. Обычный `String` не может содержать `null`, и компилятор это гарантирует.

```kotlin
var a: String = "text"
// a = null            // ошибка компиляции

var b: String? = "text"
b = null               // корректно
// println(b.length)   // ошибка: только безопасный вызов или проверка
```

Если значение пришло из Java, оно имеет *platform type* (`String!`), и ответственность за проверку лежит на разработчике — такие места стоит сразу оборачивать в nullable-тип на границе модуля.

Два способа «заявить» о nullable-возможности: `?` в типе и явная инициализация `null`.

---

## 4. Безопасный вызов `?.`

Оператор `?.` выполняет обращение, только если получатель не `null`, иначе возвращает `null`. Результат всегда nullable:

```kotlin
val b: String? = null
println(b?.length)          // null, без исключения
println(b?.uppercase()?.length)  // цепочка безопасных вызовов
```

Если нужен побочный эффект только при не-null значении, применяют `let`:

```kotlin
b?.let { println("Длина: ${it.length}") }
```

---

## 5. Оператор Элвиса `?:`

Задаёт значение по умолчанию, если слева `null`:

```kotlin
val length = b?.length ?: 0
val name = user.nickname ?: user.email ?: "Гость"
```

Правая часть вычисляется лениво — только при `null` слева. Это основной инструмент замены `if (x != null) x else default` и, что важно, замена опасному `!!`.

---

## 6. Smart cast

После проверки на `null` (или на тип) компилятор «умнеет» и позволяет обращаться к переменной как к ненулевому значению без приведения типа:

```kotlin
fun printLength(s: String?) {
    if (s != null) {
        println(s.length)     // smart cast: s уже String
    }
}

fun describe(value: Any?): String = when (value) {
    null -> "null"
    is String -> "строка длиной ${value.length}"
    is Int -> "число $value"
    else -> "неизвестно"
}
```

Ограничение: smart cast не срабатывает для `var`-свойств *другого* класса (они могут измениться между проверкой и использованием). Решение — локальная копия: `val local = obj.prop; if (local != null) ...`.

---

## 7. Выражения

В Kotlin почти всё является выражением и возвращает значение — это касается `if`, `when`, `try`, блоков `{}` (значение — последняя строка).

```kotlin
val max = if (a > b) a else b              // тернарного оператора нет
val label = when (status) {                 // when как выражение
    Status.NEW -> "Новый"
    Status.PAID -> "Оплачен"
    else -> "Прочее"
}
val parsed = try { "42".toInt() } catch (e: NumberFormatException) { 0 }
```

Функция тоже может быть выражением:

```kotlin
fun square(x: Int): Int = x * x
```

Это делает код декларативнее: вместо «вычисли и присвой» — «опиши, чем значение является».

---

## 8. Функции

```kotlin
fun finalPrice(price: Double, discount: Int): Double {
    return price * (100 - discount) / 100
}

// тело-выражение и вывод типа результата
fun finalPrice(price: Double, discount: Int) = price * (100 - discount) / 100
```

Особенности:

* модификатор видимости по умолчанию — `public`, есть `internal`, `private`, `protected`;
* `Unit` — аналог `void`, его можно не указывать;
* поддерживаются функции-расширения (`fun Product.shortInfo(): String`), локальные и вложенные функции, функции высшего порядка;
* перегрузка разрешена, но в идиоматичном коде её чаще заменяют аргументами по умолчанию.

---

## 9. Аргументы по умолчанию и именованные аргументы

```kotlin
fun formatPrice(
    value: Double,
    currency: String = "₽",
    decimals: Int = 2
): String = "%.${decimals}f %s".format(value, currency)

formatPrice(1999.0)                              // 1999.00 ₽
formatPrice(1999.0, currency = "$")              // 1999.00 $
formatPrice(1999.0, decimals = 0, currency = "€")// 1999 €
```

Именованные аргументы повышают читаемость вызовов с несколькими однотипными параметрами (`createUser(name = "A", age = 20)` вместо `createUser("A", 20)`) и позволяют пропускать параметры со значениями по умолчанию, передавая только нужные. Это также удобно для перегрузки конструкторов и функций в духе builder.

## Практическая часть. Перенос модели товара на Kotlin и устранение небезопасной работы с `null`

### Исходная «небезопасная» модель (стиль Java)

```kotlin
class Product {
    var name: String? = null
    var price: Double? = null
    var description: String? = null
    var discountPercent: Int? = null
}

fun getDisplayName(p: Product): String {
    if (p.name != null) return p.name!!      // двойная проверка + !!
    return "Без названия"
}

fun getFinalPrice(p: Product): Double {
    if (p.price == null) return 0.0
    var result = p.price!!
    if (p.discountPercent != null) {
        result = result - result * p.discountPercent!! / 100
    }
    return result
}

fun getDescription(p: Product): String {
    return p.description!!                    // упадёт, если null
}
```

Проблемы: `!!` в трёх местах (потенциальный `NullPointerException`), nullable там, где значение обязано быть (`name`, `price`), отсутствие валидации скидки, ручные проверки вместо идиом языка, нет `equals/hashCode/toString`.

### Переработанная модель

```kotlin
data class Category(val id: Long, val title: String)

data class Product(
    val id: Long,
    val name: String,                 // обязательное: не может быть null
    val price: Double,                // обязательное
    val description: String? = null,  // null допустим и осмыслен
    val discountPercent: Int? = null, // null = скидки нет
    val category: Category? = null
)
```

Здесь nullable оставлен только там, где отсутствие значения — легальное состояние предметной области. Обязательные поля защищены системой типов.

### Функции обработки

```kotlin
fun Product.displayName(): String =
    name.ifBlank { "Без названия" }

fun Product.finalPrice(): Double {
    val discount = discountPercent?.coerceIn(0, 100) ?: 0   // safe call + Elvis
    return price * (100 - discount) / 100
}

fun Product.discountLabel(): String {
    val d = discountPercent                                 // локальная копия
    return if (d != null && d > 0) "-$d%" else "без скидки" // smart cast
}

fun Product.categoryTitle(): String =
    category?.title ?: "Без категории"                      // цепочка + Elvis

fun Product.shortInfo(currency: String = "₽"): String = buildString {
    append(displayName())
    append(" — ")
    append("%.2f %s".format(finalPrice(), currency))
    description?.takeIf { it.isNotBlank() }?.let {          // safe call + let
        append(" (")
        append(it)
        append(")")
    }
}
```

### Проверка

```kotlin
fun main() {
    val products = listOf(
        Product(1, "Кофе", 599.0, discountPercent = 10,
                category = Category(1, "Напитки")),
        Product(2, "Чайник", 2499.0, description = "   "),
        Product(3, "  ", 100.0, discountPercent = 150)  // некорректная скидка
    )

    products.forEach { println(it.shortInfo()) }
    // Кофе — 539.10 ₽
    // Чайник — 2499.00 ₽
    // Без названия — 0.00 ₽  (скидка ограничена 100%)
}
```

### Что именно устранено

| Было | Стало |
|---|---|
| `!!` в `getDisplayName`, `getFinalPrice`, `getDescription` | ноль `!!`; вместо них `?.`, `?:`, `ifBlank`, `takeIf` |
| `name`, `price` могли быть `null` | сделаны non-null, ошибка ловится компилятором |
| Ручные `if (x != null)` | safe call + Elvis, smart cast |
| Некорректная скидка (150 %) давала отрицательную цену | `coerceIn(0, 100)` |
| Нет единого представления объекта | `data class` даёт `equals`, `hashCode`, `toString`, `copy` |
| Дублирование формата валюты | параметр `currency` со значением по умолчанию |

### Границы доверия

На входе из внешнего мира (Android `Intent`, JSON, Java-API) значения приходят как platform types. Там, где `null` недопустим по контракту, уместно «падать рано и понятно»:

```kotlin
val productId = intent.getStringExtra("id")
    ?: error("Не передан обязательный параметр id")

val name = requireNotNull(dto.name) { "name обязателен" }
```

То есть стратегия такая: на границе системы — явные проверки с осмысленным сообщением; внутри модели — nullable только для действительно необязательных данных; в бизнес-логике — `?.`, `?:`, smart cast без единого `!!`.

---

## Заключение

Система типов Kotlin превращает работу с `null` из набора договорённостей в проверяемое компилятором свойство программы. Разделение `val`/`var`, вывод типов, nullable-типы, безопасный вызов, оператор Элвиса и smart cast позволяют описывать модель данных так, что небезопасные состояния становятся непредставимыми, а функции с аргументами по умолчанию и именованными параметрами делают API компактным и читаемым. Практическая часть показала, что перенос даже небольшой модели товара устраняет все `!!` и делает поведение при отсутствии данных предсказуемым — что критично для мобильных приложений, где `NullPointerException` в UI оборачивается падением у пользователя.
